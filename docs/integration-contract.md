# 주문·비전·모션 연결 초안

현재 구현은 ROS2가 없는 환경에서 실행하는 Python 모의 실행기입니다.
아래 모션 형식은 ROS Service 또는 Action으로 배포되지 않았습니다.
팀 코드의 로컬 통합본에는 `POST /api/packing/pick-requests`, 요청 ID별 GET과 POST 취소 API를 추가했습니다.
팀 API는 `item_id`로 주문 품목을 검사하고, SKU를 모의 프로필 키로 대응시켜 이 모션 코어를 실행합니다.
팀 API 변경은 별도 로컬 작업본에 있으며 이 저장소에는 포함하지 않습니다.
해당 작업본의 `docs/picking-interface.md`에 요청·실행 방법이 있습니다.
실제 주문 DB, RFID 리더기, 카메라, 로봇과 연결하지 않습니다.

## 진행 순서

| 순서 | 작업 | 현재 상태 |
|---|---|---|
| 1 | 각 모듈의 책임과 요청·응답 형식 정리 | 이 문서와 `PickRequest` 검증 구현, 팀 합의 필요 |
| 2 | 가짜 박스 트리거·RFID·주문·비전과 모션 연결 | 구현 |
| 3 | 중복 실행·취소·실패·완료 수량 검사 | 자동 테스트 구현 |
| 4 | 팀 주문 코드에서 가짜 실행기 호출 | 로컬 REST API와 SKU 대응 구현. 실제 비전 Base 좌표 입력·적치 판정 합의 필요 |
| 5 | Ubuntu/ROS2에서 Action 인터페이스와 실행 워커 연결 | 미구현, ROS2 빌드·취소·타임아웃 검증 필요 |
| 6 | 실물 연결 후 TCP·툴·그리퍼 통신·교시값 검증 | 연결 시 진행 |

D455 깊이를 이용한 물체 폭 추정, 자동 열림 폭 계산과 카메라 보정은 **추후 고려사항**입니다.
현재 비전 입력은 합성 Base 좌표이며 실제 영상 인식 결과가 아닙니다.

## 모듈별 책임

| 모듈 | 입력 → 출력 |
|---|---|
| RFID | 읽은 UID → 박스 식별 키. 태그에 상품 정보를 쓰지 않음 |
| 주문 시스템 | 박스/주문 ID → 상품 ID와 수량 |
| 비전 | 상품 ID → 검증된 로봇 Base 파지 자세. 검출 실패는 명시적으로 반환 |
| 모션 | 상품 1개·목적지 슬롯·파지 자세 → 진행 단계와 성공/실패 |
| 상위 조정기 | 순서·취소·중복 요청 관리. 적치 확인 후에만 완료 수량 증가 |
| 주문/재고 시스템 | 확인된 적치 결과를 받아 DB 갱신. 모션 계층은 DB를 수정하지 않음 |

현재 팀 YOLO 출력의 픽셀 바운딩 박스를 Base 좌표로 간주하면 안 됩니다.
좌표 변환은 별도 단계이며 실제 보정 전에는 합성 입력으로 연결만 검사합니다.

## 상품 1개 모션 요청

`warehouse_motion/offline_picking/contracts.py`의 `PickRequest`가 아래 필드를 검사합니다.

```json
{
  "request_id": "DEMO-RUN-01:item:1",
  "order_id": "ORDER-DEMO-01",
  "product_id": "snack_box",
  "box_id": "BOX-01",
  "slot_id": 1,
  "grasp_posx": [400, 0, 200, 0, 180, 0],
  "frame_id": "base",
  "position_unit": "mm",
  "orientation": "zyz_deg",
  "simulation": true
}
```

- `grasp_posx`: 유한한 수 6개, `[x, y, z, a, b, c]`. 자세는 두산 ZYZ 도 단위이며 RPY로 해석하지 않습니다.
- ID는 빈 문자열을 허용하지 않고, 슬롯은 양의 정수입니다.
- 목적지 자세는 슬롯에서 결정합니다. 예시 슬롯 좌표는 실제 박스 치수·교시와 무관합니다.
- 현재 실행기는 `simulation: true`만 처리합니다.
- 수량 N개는 서로 다른 항목 요청 ID와 슬롯을 가진 N회의 단일 상품 동작으로 나눕니다.

외부 실행 요청은 주문 1건으로 받고 내부에서 이 단일 상품 모션을 반복하는 방향입니다.
현재 팀 API는 단일 상품 단위이며 주문 실행 API로 전환하는 작업이 남아 있습니다.

## 전체 모의 실행

`warehouse_motion/offline_picking/config/mock_scenario.yaml`에는 가짜 UID 하나와 상품 3개 주문이 있습니다.
실제 UID·주문·제품 DB를 읽지 않습니다. 합성 슬롯은 주문당 최대 5개입니다.
전체 시나리오는 적치 확인 수에 따라 다음 슬롯을 배정합니다. 단순 `offline_picking.mock_demo` 데모는 기본 슬롯 1을 반복 사용합니다.
슬롯 중심을 나누는 것 외에 박스별 점유·상품 크기·벽 간섭·해제 높이는 아직 계산하지 않습니다.

```text
WAIT_BOX_TRIGGER → BOX_TRIGGERED
→ SCAN_APPROACH → SCAN_RFID → RFID_READ → ORDER_LOOKUP
→ VISION_CLEAR → VISION_DETECT
→ 열림 → 접근 → 하강 → 파지 확인 → 상승 → 유지 확인
→ 경유 → 박스 접근 → 적치 → 열림 확인 → 퇴피
→ VERIFY_PLACE → PLACE_CONFIRMED → CHECK_REMAINING
→ 남은 수량 반복 → RETURN_HOME → IDLE
```

`VERIFY_PLACE`의 정상 결과도 모의 값입니다. 실제 센서로 적치를 확인하는 코드는 아직 없습니다.
손가락 열림 확인과 적치 확인을 구분하며, 적치 불명확 사례는 수량을 증가시키지 않습니다.

## 결과·이벤트

전체 실행 결과는 `protocol_version`, `request_id`, `status`, `target_quantity`,
`confirmed_quantity`, `placements`, `error_code`, `requires_reconciliation`, `trace`를 포함합니다.
`trace`의 `sequence`는 단일 실행 안에서 증가하며 네트워크 전송·영속 저장 기능은 아닙니다.

| 결과 상태 | 의미 |
|---|---|
| `completed` | 모든 모의 적치 확인 후 홈 명령까지 완료 |
| `failed` | 미등록 태그, 미검출, 빈손 파지, 잘못된 입력 또는 상태 수신 실패 |
| `cancelled` | 취소를 확인해 다음 동작 중단 |
| `needs_reconciliation` | 해제 후 실제 적치 여부를 확정하지 못한 모의 사례 |

`requires_reconciliation: true`이면 잡기 이후 완료가 확인되지 않은 항목이 있습니다.
이전에 확인된 항목 수는 유지합니다. 자동 재시도·자동 홈 복귀·자동 그리퍼 해제를 하지 않습니다.
모의 취소는 단계 사이와 그리퍼 대기 중에 검사합니다. 실물 이동 중 즉시 정지를 보장하는 기능은 아닙니다.

## 중복·동시 요청

- 동일 `MockScenario` 인스턴스에서 같은 실행 ID와 같은 UID/사례를 다시 보내면 저장된 결과를 반환합니다.
- 재응답은 `replayed: true`이며 추가 모의 이동·이벤트 발생이 없습니다. 실패/불명확 결과도 재실행하지 않습니다.
- 같은 ID에 다른 UID/사례를 보내면 거부합니다. 다른 작업이 실행 중이면 `BUSY`로 거부합니다.
- 이력은 메모리에만 있습니다. CLI를 새로 실행하거나 프로세스가 재시작되면 이력이 사라집니다.
- 실물·DB 연동 전에 실행 이력 영속화, 재시작 후 상태 대조, 주문 결과의 중복 반영 방지와 복구 승인을 구현해야 합니다.

2. 박스별 슬롯 배정·점유·공간 부족 처리. 실제 상품·툴 크기를 반영한 배치와 경로 검증 필요.
3. RFID UID → 박스 → 주문 매핑과 실제 비전 Base 좌표 입력 연결.
4. 팀 SKU와 YOLO 클래스 대응 확정. 현재 5종 모의 SKU 대응표는 실물 검증을 대체하지 않음.
5. 적치 성공 판정과 복구 주체, 요청 이력 영속화와 주문·재고 결과 중복 반영 방지.
6. ROS2 Action의 필드·타임아웃·취소/정지 응답, 화면 일시정지·취소 연동.
